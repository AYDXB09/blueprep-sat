blueprep — concept review

What the tool solves now, and where it grows next

A single-file, single-machine SAT practice player built around a real, official question bank. The core loop already works — this maps what's solid today against what a rebuild would actually add, not just restate.

Today

Solved already

Real, current question bank

A downloader pulls live inventory from the source's public question bank API, resumes from a checkpoint if interrupted, and flags questions that also appear in official full-length practice tests.

scripts/download-questions.js

Bluebook-style test player

Practice sets are assembled on the fly, with the strike-through, highlighter, and instant-feedback interactions the real digital SAT uses — not a generic quiz UI.

buildPracticeSet · index.html

Mistake log that self-corrects

Wrong answers are logged automatically; a later correct answer on the same question clears it, a repeat wrong answer re-marks it. Review navigation jumps straight to logged mistakes.

Constraint

What that architecture caps out at

Progress lives in a local JSON file

Answer history and sessions are written to data/progress.json / sessions.json on whatever machine ran the server. Nothing syncs, nothing survives a fresh clone.

No accounts, so no "whose attempt is this"

Every user on the box shares one history. There's no login, so multi-student or multi-device use isn't a supported case — it's a single-player local tool by construction.

170KB of markup carrying the whole UI

The player, review pages, mistake log, and AI panel all live in one index.html. It works, but every new feature adds to a file that can't be split, tested in isolation, or reused as components.

Numbers, no trend

Per-question analytics exist, but there's no view of accuracy or pace over time — no way to see a section score climbing across ten practice sets.

Not deployable as-is

server.js expects a filesystem it can write to. That's fine on a laptop; it rules out putting this behind a public link for anyone else to try.

enhancement path

Three tiers, each unlocked by the one before it

This is a dependency order, not a wish list — componentizing has to happen before accounts make sense to wire in, and accounts have to exist before there's per-user history worth charting.

Componentize the player

React + Vite + TypeScript

Port the existing Bluebook-player logic — ordering, scoring, strike/highlight interactions — out of the single HTML file and into components. Same behavior, testable in isolation, ready to hold new state.

Give it accounts

Supabase — Postgres + Auth

Replace progress.json with users / test_attempts / question_responses tables. This is the actual "SaaS" step: attempts are tied to a person, and follow them across devices and sessions.

Show the trend, ship the link

Recharts · Vercel

Score-over-time and section-breakdown charts turn the mistake log into a visible improvement curve. Deploying to Vercel makes it something a reviewer can actually open, not just read about.
